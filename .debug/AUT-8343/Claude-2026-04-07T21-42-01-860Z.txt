## Ticket: AUT-8343
**Summary**: Autofill 3.1(d) from GSTR-2B vs Purchase Reco to fix missing RCM liability
**Acceptance Criteria**:
## Description

Right now, when a user reconciles their GSTR-2B with the Purchase Register and accepts invoices that are "Not in Purchase Register", those invoices automatically get added to ITC (table 4). That part works fine.

But here's the issue — those same invoices are RCM invoices, which means the user is also supposed to declare them as a liability in table 3.1(d). That never happens automatically. The user has to manually figure out and fill 3.1(d) themselves.

So the return ends up in a broken state:

ITC is claimed in table 4 ✓ RCM liability in 3.1(d) is missing ✗

This is a compliance risk. The GST return is incomplete and incorrect.

## User Story

We will add an inline autofill control directly inside the 3.1(d) row — so the user can choose their source and fill just that row without affecting anything else in table 3.1.

The control will have a small dropdown with two options:

- Purchase register — pulls RCM invoices from the purchase register (existing behaviour, just now available at row level)

- GSTR-2B vs Purchase Reco — pulls invoices that the user has already accepted as "Not in Purchase Register" in the reco, filters only RCM-applicable ones, and fills 3.1(d) with the aggregated taxable value and tax amounts


Once the user selects a source and clicks Apply:

- The values populate in 3.1(d)

- A small label chip appears in the row showing which source was used (e.g. "2B vs PR reco") so the user has a clear audit trail

- The dropdown and Apply button collapse — a "Clear" option appears if they want to reset

## Edge Cases to Handle:

- **No RCM invoices found **— if the user selects "GSTR-2B vs Purchase Reco" but there are no accepted RCM invoices for that GSTIN and period, show a clear message like "No accepted RCM invoices found in 2B vs PR reco for this period". Do not silently fill zeros.

- **Values already exist in 3.1(d) **— if the user has already filled 3.1(d) manually or via another autofill, show a confirmation before overwriting: "3.1(d) already has values. Do you want to replace them?"

- **Mixed invoices in reco** — not all accepted invoices in reco are RCM. Regular invoices must be excluded. Only invoices where the supplier has marked the supply as RCM in their GSTR-1 should be picked up.


## Acceptance Criteria:

-  3.1(d) row shows an inline dropdown with exactly two options: "Purchase register" and "GSTR-2B vs Purchase Reco"

-  When "GSTR-2B vs Purchase Reco" is selected and applied, 3.1(d) is filled with aggregated values from accepted RCM invoices in the reco for that GSTIN and period

-  Non-RCM accepted invoices are excluded from the autofill

-  A source chip appears in the 3.1(d) row label after autofill, showing where the data came from

-  If no qualifying invoices exist, an appropriate empty state message is shown — no silent zero fill

-  If 3.1(d) already has values, the user is asked to confirm before overwriting

-  Clicking Clear resets 3.1(d) and restores the dropdown to its default state

-  ITC in Table 4 is unaffected

-  No change to rows 3.1(a), (b), (c), (e) or the global Sales register autofill button

### Risks

- **[HIGH] New backend API not yet delivered**: `POST gst-returns/3b/fill-3-1-d-from-reco/` does not exist yet. Frontend development can proceed with the contract `{ txval, igst, cgst, sgst, cess, invoice_count }`, but integration testing is blocked until the backend delivers.
- **[HIGH] Row identification fragility**: The `nature_of_supplies` string for `(d)` is backend-controlled. Using `record.nature_of_supplies.startsWith('(d)')` is reasonable, but if the backend changes the prefix format, the feature breaks silently. The spec acknowledges this with a constant + `startsWith` fallback.
- **[MEDIUM] Purchase Register source extracts from global refresh**: The "Purchase Register" option reuses `GET gst-returns/3b/refresh-table-three-one/` which returns ALL rows. Extracting only `(d)` from the response avoids modifying other rows, but the server-side effect of this call (if any state mutation happens on the backend) could affect other rows. Need to verify the refresh endpoint is side-effect free for read operations.
- **[MEDIUM] Race condition with global refresh**: If the user clicks the global "Autofill using Sales register" button in the `TableWrapper` header while an inline 3.1(d) autofill is in progress (or vice versa), both will attempt to write to `tableData`. The global refresh calls `updateData()` which replaces all rows via parent, while the inline only modifies the `(d)` row locally. The global refresh would overwrite the inline autofill values.
- **[LOW] Pre-autofill value storage**: The spec says "Clear" restores pre-autofill values. Need to store the `(d)` row snapshot before each autofill. If the user does multiple autofills without clearing, the "original" reference should be the values before the very first autofill.
- **[LOW] `getColumns` parameter expansion**: `getColumns()` currently takes 2 params (`isEditEnabled`, `updateRecord`). Adding 5+ new params will make it unwieldy. Consider passing an options object, following the pattern from other column files in the codebase.

---

Modify `OutwardInwardSupplies/index.tsx` to add three new state variables: `autofill31dSource` (tracks the applied source or `null`), `autofill31dLoading` (loading flag), and `preAutofill31dValues` (snapshot of the `(d)` row before autofill). Add `onAutofill31d(source)` that checks for non-zero values and either calls the API directly or triggers the confirmation via `AppPopConfirm`. For the "Purchase Register" source, call the existing refresh endpoint and filter only the `(d)` row from `sup_details`. For the "Reco" source, call the new `POST` endpoint. After success, update only the `(d)` row in `tableData` using the existing `updateRecord` pattern and set the source state. In `TableColumns.tsx`, expand `getColumns` to accept an options object with the new state/callbacks. In the `nature_of_supplies` column, add a `render` function that checks `startsWith('(d)')` and renders the `AppSelect` dropdown (when no source is applied) or the `AppStatusBadge` + Clear link (when a source is applied). Add the new response type to `libs/constants/src/models/GstReturns/3B/index.ts` and the two Mixpanel functions to `libs/services/mixpanel/src/SMB/GSTModule/GSTR.ts`.
