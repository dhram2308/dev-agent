## Ticket: AUT-8343
**Summary**: Autofill 3.1(d) from GSTR-2B vs Purchase Reco to fix missing RCM liability
**Acceptance Criteria**:
## Description

Right now, when a user reconciles their GSTR-2B with the Purchase Register and accepts invoices that are "Not in Purchase Register", those invoices automatically get added to ITC (table 4). That part works fine.

But here's the issue — those same invoices are RCM invoices, which means the user is also supposed to declare them as a liability in table 3.1(d). That never happens automatically. The user has to manually figure out and fill 3.1(d) themselves.

So the return ends up in a broken state:

ITC is claimed in table 4 ✓ RCM liability in 3.1(d) is missing ✗

This is a compliance risk. The GST return is incomplete and incorrect.

## User Story

We will add an inline autofill control directly inside the 3.1(d) row — so the user can choose their source and fill just that row without affecting anything else in table 3.1.

The control will have a small dropdown with two options:

- Purchase register — pulls RCM invoices from the purchase register (existing behaviour, just now available at row level)

- GSTR-2B vs Purchase Reco — pulls invoices that the user has already accepted as "Not in Purchase Register" in the reco, filters only RCM-applicable ones, and fills 3.1(d) with the aggregated taxable value and tax amounts


Once the user selects a source and clicks Apply:

- The values populate in 3.1(d)

- A small label chip appears in the row showing which source was used (e.g. "2B vs PR reco") so the user has a clear audit trail

- The dropdown and Apply button collapse — a "Clear" option appears if they want to reset

## Edge Cases to Handle:

- **No RCM invoices found **— if the user selects "GSTR-2B vs Purchase Reco" but there are no accepted RCM invoices for that GSTIN and period, show a clear message like "No accepted RCM invoices found in 2B vs PR reco for this period". Do not silently fill zeros.

- **Values already exist in 3.1(d) **— if the user has already filled 3.1(d) manually or via another autofill, show a confirmation before overwriting: "3.1(d) already has values. Do you want to replace them?"

- **Mixed invoices in reco** — not all accepted invoices in reco are RCM. Regular invoices must be excluded. Only invoices where the supplier has marked the supply as RCM in their GSTR-1 should be picked up.

### Risks

#### [HIGH] Global Refresh Overwrites 3.1(d) Autofill Values — Silent Data Loss

The `MainOptions.tsx` global "Autofill GSTR 3B" button calls `gst-returns/3b/refresh/` which returns the **entire** `ThreeBDetailsProps` object and spreads it into parent state via `setData(data.data)`. This triggers `useEffect(() => { setTableData(data); }, [data])` in `OutwardInwardSupplies/index.tsx:40-42`, **completely overwriting local `tableData`** including any values populated by the 3.1(d) inline autofill. The user receives no warning. This is a **critical data loss path** that affects the core feature.

**Mitigation**: The 3.1(d) autofill must immediately call `updateData()` to persist values to parent state (not just local `tableData`). Additionally, consider auto-saving to backend after autofill, or guard the `useEffect` to not overwrite when autofill is active.

#### [HIGH] Autofill Values Are Unsaved Until Manual "Save" Click — No Persistence Guarantee

The autofill will update local `tableData` state, but there is no mechanism to auto-persist. The user must click the "Save Changes" button in the `TableWrapper` header (which only appears in edit mode). However, the spec says the dropdown is **hidden during edit mode** (`isEditEnabled === true`). This creates a **workflow contradiction**: the user applies autofill (outside edit mode), the values sit in local state, but the save button only appears inside edit mode. The values are at risk of being lost on any re-render, navigation, or global refresh.

**Mitigation**: After autofill, immediately call `postDataApi('gst-returns/3b/edit-table-three-one/', ...)` with the updated `tableData` to persist, OR call `updateData()` to sync to parent. The EligibleITC pattern auto-saves after autofill — follow that.

#### [HIGH] No Unsaved Changes Warning on Page Navigation

There is **no `onBeforeUnload`, `isDirty` flag, or navigation guard** anywhere in the 3B module. If the user applies 3.1(d) autofill and navigates away (back button, route change, tab close), all values are silently lost. This is an **existing architectural gap** in the 3B module, not new to this feature, but this feature amplifies it because the autofill is a multi-step action that gives users a false sense of persistence.

#### [HIGH] "Purchase Register" Source — Extracting Only (d) Row From Full 3.1 Refresh Is Fragile

The "Purchase Register" option reuses `gst-returns/3b/refresh-table-three-one/` and extracts only the (d) row from the `sup_details` array. Row matching relies on `nature_of_supplies.startsWith('(d)')` string matching. If the backend changes the label text (e.g., from `"(d) Inward supplies (liable to reverse charge)"` to `"(d) Inward Supplies..."` with different casing), the match breaks silently. More critically, calling this endpoint **returns all 5 rows** — the implementation must carefully **only apply the (d) row** and discard (a), (b), (c), (e) to avoid overwriting other data.

**Mitigation**: Use `NATURE_31D_PREFIX = '(d)'` constant with `startsWith()` as planned. Add an explicit guard that if no matching row is found, show an error rather than silently failing.

#### [HIGH] New Backend API Not Yet Delivered — `fill-3-1-d-from-reco/`

The `POST gst-returns/3b/fill-3-1-d-from-reco/` endpoint is a **new API that must be built by the backend team**. There is no existing endpoint for this. The response shape (`{ txval, igst, cgst, sgst, cess, invoice_count }`) is assumed but unconfirmed. If the backend returns a different structure (e.g., nested under `data`, or uses `tax_value` instead of `txval`), the frontend will fail.

**Mitigation**: Add the `ThreeB31dAutofillResponse` type now, but implement defensive parsing. Coordinate with backend team on exact response contract before integration testing.

#### [MEDIUM] `AppPopConfirm` Placement in Table Cell May Clip or Overflow

`AppPopConfirm` defaults to `placement='top'` with `maxWidth: 500px` and `zIndex: 2000`. When rendered inside a table cell (the `nature_of_supplies` column), the popconfirm may clip against the table border or card container. The 3.1(d) row is typically the 4th of 5 rows, so there's limited space below. With the confirmation message "3.1(d) already has values. Overwrite with {source name}?", the popover will be moderately sized.

**Mitigation**: Use `placement='bottomLeft'` or `placement='right'` explicitly. Test with actual table layout.

#### [MEDIUM] `nature_of_supplies` Column Gets Crowded With Dropdown + Badge + Label

The current `nature_of_supplies` column has no explicit width and renders only text. Adding an `AppSelect` (180px wide), an `AppStatusBadge` (min 70px), and a "Clear" button alongside the row label text in the same cell creates a crowded layout. At smaller screen widths, elements may wrap or overflow.

**Mitigation**: Use `Space` or `Flex` wrapper with `wrap` for the cell content. Consider placing the dropdown below the label text rather than inline. Test at 1280px viewport width.

#### [MEDIUM] Edit Mode + Autofill State Interaction — Cancel Resets Autofill Values

If user applies 3.1(d) autofill (values + source badge appear), then enters edit mode, makes changes, and clicks "Cancel" — the `onEditEnabled(false)` handler at line 54-58 calls `setTableData(data)`, resetting to the **parent's data**. If the autofill values weren't persisted to the parent via `updateData()`, cancel will **destroy the autofilled values** and remove the source badge.

**Mitigation**: Autofill must sync to parent state immediately. Store `autofill31dSource` separately so it persists through edit cancel.

#### [MEDIUM] Race Condition: Rapid Source Selection

If user selects "Purchase Register", API starts loading, then quickly switches to "GSTR-2B vs Purchase Reco" before the first call completes — two API calls will be in flight. The first response may arrive after the second and overwrite the correct values.

**Mitigation**: Use `autofill31dLoading` to disable the dropdown during API calls. Consider an `AbortController` or response-timestamp check.

#### [LOW] Mixpanel Event Names Are Speculative

The event names `onMPGSTR3bPrepareAutofil31dPR` and `onMPGSTR3bPrepareAutofil31dReco` are proposed in the spec but must be confirmed with the analytics team. Existing events follow patterns like `onMPGSTR3bPrepareAutofilfrmSales`, `onMPGSTR3bPrepareAutofilfrm2B`. The "31d" naming is consistent but novel.

#### [LOW] `ThreeBItemProps.txval` Is `number | string` Union Type

The type definition at `libs/constants/src/models/GstReturns/3B/index.ts:41` defines `txval?: number | string`. When the new API returns `txval: number`, it must be compatible with how `TableColumns.tsx` renders values (it calls `parseFloat(value)` which handles both, but also checks `value === 'blank'`). The autofill should set numeric values, matching the API response shape.

#### [LOW] CGST/SGST Auto-Sync in Edit Mode Doesn't Apply to Autofill

In `TableColumns.tsx:104-108`, editing CGST auto-sets SGST (and vice versa). This only applies during `isEditEnabled` mode. The autofill sets values directly without triggering this sync. This is **correct** behavior since the API returns already-calculated values, but should be documented.

### Recommended Approach

Follow the **EligibleITC autofill pattern** but with a much simpler, single-row-scoped implementation. Add `autofill31dSource` and `autofill31dLoading` state to `OutwardInwardSupplies/index.tsx`. Modify `getColumns()` to accept these plus `isLock`, and conditionally render the dropdown + badge in the `nature_of_supplies` column for the `(d)` row. **Critically**, after any successful autofill API call, immediately call both `setTableData(updatedData)` AND `updateData(updatedData)` to persist to the parent state — this prevents the global refresh and edit-cancel data loss scenarios. For the "Purchase Register" source, reuse the existing `refresh-table-three-one` endpoint but surgically extract only the (d) row. For "GSTR-2B vs Purchase Reco", call the new endpoint and map the flat response into the (d) row. Wrap the apply action in `AppPopConfirm` only when existing values are non-zero. Store pre-autofill values for the "Clear" action. Keep `autofill31dSource` in component state (not in the data model) since it's a UI-only concern.

This leaves the GST return in an incomplete state: ITC is claimed without the matching RCM liability declaration, creating a compliance risk. Users must manually calculate and fill 3.1(d), which is error-prone and defeats the purpose of the reconciliation workflow. Adding an inline autofill control scoped to the 3.1(d) row closes this gap without disrupting any other part of Table 3.1 or the existing global Sales Register autofill.

- **New response type** (`ThreeB31dAutofillResponse`) added to the GSTR-3B models.
